## 1. 下载、运行现有两端

在 Mac 上获取项目：

```sh
git clone https://github.com/ZZ9622/nucleo-pet-fw.git
cd nucleo-pet-fw
```

### STM32

沿用 [现有接线指南](../WIRING_zh.md)，先保证原有宠物程序运行正常。
准备好 Arm 编译器、CMake、OpenOCD 后，在仓库根目录执行：

```sh
make test
make build
make probe
make flash
```

确认 `make probe` 识别到目标板后再烧录。此处烧录的仍是原有固件，不含手机通信功能。

### iPhone App

1. 使用与你的 macOS 兼容的 Xcode，安装一个 iOS 模拟器运行时。
2. 打开 **`ios/NucleoPet.xcodeproj`**，Scheme 选 **NucleoPet**。
3. 先选 iPhone 模拟器，按 **⌘R**，体验小屋与往返。
4. 测试入口：Xcode **⌘U**；共享核心测试命令见 [App README](../ios/README.md)。
5. 真机运行需在 Signing & Capabilities 中选择自己的 Team，并按需设置唯一 Bundle Identifier。
6. 真正的硬件链路以实际 iPhone 和实际开发板作为验收设备。

## 2. 先选定通信路径

当前硬件是 NUCLEO-F401RE、OLED 与按钮。开发板没有板载 BLE，现有固件也没有无线通信代码。
板载 ST-LINK 的 CN1 USB 目前用于 Mac 供电、烧录和调试，不是已经完成的 iPhone 同步通道。
开发板接口参考 [ST 官方资料](https://www.st.com/en/evaluation-tools/nucleo-f401re.html)。

可优先评估以下原型路径，**最终接线与代码须在确认模块型号后确定**：

```text
iPhone App（Core Bluetooth）
          ↕ BLE GATT
提供兼容 GATT 服务的 BLE 模块或桥接板
          ↕ 约定好的 UART 或 SPI 协议
STM32 NUCLEO-F401RE
```

这是一条建议评估的接入路径，仓库没有包含该 BLE 模块的驱动。
先确认模块支持的数据服务、通知、分包、吞吐量和引脚电平，再选定与 STM32 的连接方式。
当前接线规划保留 PA2/PA3，但固件尚未配置它们用于手机链路。
不要因为看到“蓝牙串口”就默认它已经具备 iPhone 所需的服务。
iOS 侧参考 [Apple Core Bluetooth](https://developer.apple.com/documentation/corebluetooth)。

## 3. 需要改动的具体入口

| 文件 | 接手时要做的事 |
| --- | --- |
| `ios/App/JourneyDeviceViews.swift` | 将体验设备说明扩展为真实设备选择、连接状态和明确的演示／实物模式 |
| `ios/App/TravelView.swift` | 用真正的状态交接替代约 1.1 秒等待与模拟确认，处理断连与失败 |
| `ios/App/CompanionStore.swift` | 接入真实传输适配层；收到持久化确认后再发布所有者变更 |
| `ios/Sources/PetDomain/CompanionSession.swift` | 新增真实设备绑定和完整状态导入，保留板端 petID；当前初始化会创建体验 UUID |
| `ios/Sources/PetDomain/FirmwareState.swift` | 作为显式字段映射参考，校验版本、属性范围和计时累计 |
| `src/main.c` | 加入非阻塞通信调度；宠物离开或交接期间停止本地照顾与状态推进 |
| `src/board.c` 及新的通信模块 | 配置选定的外设、接收缓冲、消息边界和超时，保留 OLED 与按键引脚 |
| 板端新增身份与存档模块 | 保存稳定 petID、完整状态、居所、revision 和待完成事务 |
| 板端显示逻辑 | 宠物去手机后显示出门提示，确认返回后再恢复宠物画面 |

不要只在连上 BLE 后调用当前模拟 `finishTransfer`：那仍然只是切换手机里的体验状态，
没有导入真实板端宠物，也没有保证两端只存在一个活动所有者。

## 4. 双端状态交接的最低约定

完整设计见 [`ios/docs/HANDOFF.md`](../ios/docs/HANDOFF.md)。至少要对齐：

- 稳定的宠物 ID、设备绑定关系、序列化版本、规则版本、当前所有者、revision、transferID。
- `PetState` 的完整字段，包括每日喂食计时、睡眠／清醒累计、自动入睡进度、经验等；
  不能只发送 Happiness 和 Energy，也不能只发送显示用的 `PetSnapshot`。
- 使用明确字段编码，不直接复制 C struct 的内存；协商分包、长度、校验与重组超时。
- 接收端先可靠保存，再确认接收；来源端在交接过程中冻结，双方都按事务 ID 去重。
- 回执丢失后查询事务状态；不能仅因超时，就让两边同时恢复为宠物所有者。
- 明确通电计时、手机时间和断电时间的计算方式，避免往返时重复衰减或重复恢复。

当前 App 的“撤销旅程”只对单进程模拟安全。真实链路一旦可能已经完成接收，
必须先查询和协调事务，不能原样套用这个撤销方法。

## 5. 推荐联调顺序

1. **只读连通**：真实 iPhone 能读到开发板身份及当前属性，先不改变状态。
2. **一项照顾指令**：手机发送一次摸摸，板子执行一次、返回确认；重复同一消息不重复加属性。
3. **接到手机**：板端冻结／显示出门，App 导入同一 petID 与完整状态后确认接管。
4. **送回挂件**：App 交出最新状态，板端保存并确认后恢复；App 停止本地照顾。
5. **断连与断电**：逐步测试每一个交接阶段中断，再重连、重开 App、复位开发板。

第 2 步是通信验收；第 3、4 步才是“宠物真的跑到手机／回到挂件”的验收。

## 6. 实物验收清单

- [ ] 手机连接的是指定的真实开发板，界面明确区分体验模式。
- [ ] 同一个动作只执行一次；错误、重复、乱序、未完成的消息不会重复增加属性。
- [ ] 往返前后 petID、心情、精力、睡眠和内部计时保持连续。
- [ ] 任一时刻只有一个活动所有者；另一端显示出门状态并拒绝照顾。
- [ ] 传输中断、手机后台终止、双方断电后能恢复或明确提示处理，不偷偷创建新宠物。
- [ ] 睡眠、瘫软救助、每日喂食期限在往返后仍与固件规则一致。
- [ ] 既有 OLED、四键、闲置熄屏和 SWD 烧录仍可工作。

目前已通过的范围是 App 的 14 项逻辑测试与 3 项 iPhone 模拟器界面测试。
真实通信的以上清单应由联调者实测后逐项记录，不提前标记通过。
